# Runtime architecture

One Rust process serves the entry redirect at `/`, the full game at `/play.html`, all browser modules/assets, `/LICENSE`, the account/community API, and multiplayer WebSockets. `cargo run --release` starts everything on port 8080 by default; `PORT=80` selects port 80. There is no separate frontend server or proxy process. The entry page immediately opens the game title screen; there is no separate marketing page to navigate.

The browser uses standard ES modules and browser APIs. There is no bundler, CDN, runtime package dependency, texture download, or generated model file. Static meshes are assembled into spatial chunks once, uploaded to WebGL buffers, and culled by distance. Actors and effects use a small dynamic buffer. The canvas requests WebGL2 first and translates the shaders to GLSL ES 3.00; the WebGL1 path uses GLSL ES 1.00. Render resolution is adjustable independently of CSS layout.

The visible UI uses `webgl-ui.js`: a separate transparent WebGL surface at up to 2× device resolution, independent of the world quality setting. It batches colored rectangles, clipped pixel glyphs, and textures for existing maps/icons/heraldry. `pixel-font.js` supplies original editable bitmap glyphs, with local Unicode font fallback for international text. No hosted font, UI framework, rasterized HTML snapshot, or build step is involved.

`play.html` and `style.css` describe the responsive semantic controls. Their paint is suppressed only after the UI renderer initializes; their layout rectangles drive GPU geometry. Native focus, text entry, selection, composition, form validation, touch scrolling, controller navigation, and accessibility remain available. The painter handles visible fields, selection/carets, focus rings, scrollbars, select popovers, and tooltips. It caches panel geometry until mutations, focus, scrolling, or resizing change it; moving labels update with the scene, maps upload at 10 Hz, and removed panels release their GPU resources. A lost UI context exposes the readable semantic controls until restoration reloads the client.

Community drafts are bounded in-memory state, keyed by character, section, form, and destination. They survive panel navigation, are removed after an acknowledged submission, and are cleared on character change. No draft is stored in local storage. Transaction retries keep the existing idempotent server request ID. Guild roles, authority, economic checks, and all API payloads retain their server contracts.

`live-social.js` adds a HUD conversation window, speech bubbles, and four gestures to the existing articulated character rig. The server's `live_social.rs` derives Nearby's 35 m audience and Zone's district/biome audience from authoritative positions, enforces instance isolation and bilateral player blocks, and limits accepted messages/gestures to one every two seconds. Zone uses the same district boundary rules as `World.district`; it reaches the whole crew inside an expedition. Nearby bubbles require a currently visible actor, range, and line of sight; zone messages stay in the conversation window. Gesture animation lasts four seconds, bubble text eight, and reduced motion uses a static pose.

Version-2 socket actions `chat` (`channel`, `body`, `requestId`) and `emote` (`gesture`, `requestId`) accept at most 280 text characters and a fixed gesture allowlist. Author names, positions, zones, and instance IDs come from the server. Snapshots add `chatContext` and a `social` array of accepted messages or request-specific rejections. Each player retains up to 32 pending deliveries, drained only when a snapshot enters the socket queue; a prolonged backlog drops the oldest entries. The last 16 request receipts make retries idempotent within the connection. The client keeps 80 history entries, 256 deduplication IDs, and at most 64 bubble entries; entering or leaving an instance clears the visible conversation. Nearby and zone drafts clear only on acknowledgement and are isolated by character. Chat text, gestures, and delivery receipts are transient. The additive `socialTutorial` character field saves only the three optional exercise flags through normal gameplay checkpoints; old saves default to unlearned. These exercises never gate contracts or grant rewards.


The renderer derives daylight from the real UTC timestamp modulo 86,400,000 ms. Snapshots synchronize a monotonic browser clock to the server's Unix milliseconds; the title screen uses the device clock until synchronization. Animation time and gameplay tick time do not advance the day/night cycle. The same daylight values drive sun/moon direction, sky, surface illumination, fog, and the displayed clock. Atmospheric light uses directional scattering and four analytically intersected Commons lamp volumes, clipped at the visible opaque surface. It allocates no extra render target and uses no ray marching. Low render quality omits lamp volumes; Settings can disable atmospheric light entirely. This is a lightweight approximation, without volumetric shadow maps or a measured frame-rate guarantee.

## Authority and prediction

`CityLife` samples deterministic civilian routes against the synchronized UTC clock. It generates nearby block residents on demand, retains 36 authored neighborhood regulars, and limits the visible population to 64 (30 on low quality). Route segments use streets, doorways, interior aisles, building stairs, outdoor slopes, and skyway floors. Stair segments sample the same discrete tread height as movement. Each public building adds an upstairs courier and tenant. Scene groups return to a shared meeting point at the end of each three-minute cycle, so a scene change does not teleport them. Visible hostiles interrupt a routine; bounded, collision-checked escape steps are retraced before the paused route resumes. Conversation pauses are local. Old block definitions and reaction state are released as the viewer moves; frustum culling and a shorter detail radius limit civilian mesh work. Civilians have no combat hitboxes, inventory, quest authority, or persistent simulation state.

The five neighborhood stories add ordinary quests and fixed stewards to the existing content. Their completion IDs derive the viewing character's street activity and service-light state; saved moral decisions select the remembered settlement and resident treatment. Reconnecting restores this presentation from server progress without a new save format. Rotating street scenes and their matching work props use UTC in three-minute slots; day/night duties use 06:00–20:00 UTC as the working period. Personal story presentation and transient crowd reactions can differ between players; this is not a shared resource or population simulation. Decorative workspaces add no new authoritative collision solids.

All play requires a signed-in server character and a live world connection. The browser's `Prediction` class uses the map recipe and movement rules to move the avatar responsively. Client `world.js`/`prediction.js` and Rust `World`/`terrain.rs` share the stair, slope, floor-opening, ceiling, and visibility rules. The Rust shard computes authoritative positions, collisions, abilities, target range, line of sight, damage rolls, enemy AI, quests, talent spending, purchases, inventory, and XP. The server accepts movement intentions and actions, never submitted character state or XP totals. Browser saves, local signing identities, and a separate local gameplay simulation are absent.

Client prediction moves the local avatar only. It does not damage actors, award XP, advance objectives, or regenerate resources. Server snapshots replace authoritative state; large position differences snap to the server position and small differences are blended. This is a basic prediction scheme, not a full input-history rewind/replay implementation.

`POST /api/register`, `/api/login`, `/api/logout`, and `/api/characters` use JSON and a same-origin request marker. `GET /api/session` and `/api/characters` read the authenticated account. `DELETE /api/characters/{id}` deletes an owned, disconnected character after checking guild/party membership and unsettled economic obligations. `GET /api/world` upgrades to a WebSocket after checking session and Origin. The socket's first message is `{ "type": "join", "version": 2, "id": "<character id>" }`; subsequent commands and snapshot/event envelopes also carry version 2.

Movement messages contain `type`, `sequence`, `forward`, `strafe`, `yaw`, `jump`, `dash`, and `sprint`. Forward/strafe values are clamped and yaw must be finite. The server discards old sequence numbers and stops input after 300 ms without a movement command. Actions are `ability`, `quest`, `interact`, `lift`, `talent`, `workOrder`, `medkit`, `buy`, `respawn`, and `intro_seen`. The client sends inputs at 20 Hz and receives snapshots at 10 Hz. Messages are JSON with bounded input size.

Character creation checks callsigns against every saved character under the same database mutation lock used for creation and deletion. Comparison trims outer whitespace and applies Unicode upper/lower case mappings; the displayed name retains its chosen case. The lock stays held through the character and account writes, so simultaneous requests cannot claim the same name. This includes disconnected characters and characters that have never entered the world. Successful deletion releases the name. Existing characters are not renamed.

`tutorial.rs` starts new characters in the map’s training courtyard. Saved `tutorialStage` advances from authoritative movement, ordinary proximity-checked terminal interactions, and a range-checked Shoot action against the practice target. That target is a stationary training prop and has no enemy AI, kill credit, or loot. Combat cannot target players in the courtyard, and attacks from it cannot damage enemies. Using the exit clears the tutorial stage and movement state before relocating the player to the existing Commons spawn. Older characters have no tutorial stage and continue their existing story. The client predicts movement and displays saved guidance; it cannot submit tutorial progress or rewards.

### Ghostline authority and lifetime

Ghostline uses the existing `{ "type": "ability", "id": "ghostline", "version": 2 }` command. The server records positions produced by its movement simulation; clients cannot submit a route, contact, damage amount, or reward. Each player retains at most six seconds of movement, sampled every 100 ms (61 points at the default settings), and can own one active echo. Casting requires two seconds and 12 m of recent movement, sufficient energy, and the normal ability/global cooldown checks. The route is copied at cast time and replayed against shard time. Client prediction neither records authoritative routes nor resolves braids; the browser renders the routes in snapshots.

Contact sweeps the player and echo between ticks, clipped to the echo’s arming and expiry times, so a fast crossing cannot skip the trigger. Checks use three-dimensional distance, map collision, and line of sight. The nearest contact wins; equal distances break by character ID. Simultaneous echoes resolve in owner-ID order. The echo is consumed before damage and resource recovery. A second runner multiplies attack power by 1.5; the creator retains normal kill rewards, while each distinct participant receives one capped energy recovery and dash reset. Attacks use the existing combat resolution and check visibility from the contact point to each enemy.

Version-2 snapshots add `ghostlines`, `ghostCharge`, and `dashReady`. Each ghost carries its owner, display name, start time, and relative-time position samples. Up to eight nearby ghosts are sent, prioritizing the viewer’s own echo; their full routes in snapshots allow recovery from dropped presentation events without a separate replay cache. A `braid` event supplies the shockwave and participant feedback. Death, lifts, disconnects, and expiry discard active echoes; recordings never enter character saves or signed exports. The existing persisted ability cooldown map includes `ghostline`, preventing online reconnects from resetting its cooldown. Ghostline is confined to the owner’s shard, like other world combat. Dense echo traffic and device rendering still require capacity testing.

## CPU and network model

Tokio handles HTTP and WebSockets on a configurable multithreaded scheduler. Each world shard runs on its own named OS thread using the shared runtime's handle for timers and asynchronous storage jobs. Simulation and snapshot CPU work therefore stay off the networking worker threads. Each shard owns its mutable players and enemies; simulation does not take a global player lock. A bounded command channel carries socket input into each shard. The deterministic character-ID hash assigns a character to a stable shard for a given configured shard count. Changing the shard count changes that assignment at the next connection.

Each shard runs fixed 50 ms simulation ticks and skips missed scheduling ticks rather than building an unlimited catch-up queue. Spatial buckets select nearby player representations within 180 m, capped at the nearest 64. Enemy counts are currently small and scanned directly. Snapshot assembly copies public guild badges under one short shared lock, then performs spatial filtering and JSON construction after releasing the lock. Snapshots go through four-slot per-connection output queues; full queues drop messages rather than grow memory without a bound. Slow socket writes time out. Critical state is retained in the next snapshot even if a presentation event is dropped.

The default HTTP/WebSocket worker count is available CPU parallelism capped at four. The default world thread count reserves those workers and one expedition thread, with a minimum of one and a maximum of 64 world threads. `SLOPERBERPUNK_WORKERS` and `SLOPERBERPUNK_SHARDS` override the counts independently. Each shard allows 256 players. A 16-shard configuration provides 4,096 ordinary-world slots plus a separate 256-slot expedition shard; **that arithmetic is not a throughput benchmark**, and a full home shard still rejects a new connection. CPU time, JSON serialization, densely populated areas, socket memory, bandwidth, and disk latency still constrain real capacity. Ordinary party membership does not migrate characters. The dungeon finder uses the bounded transfer below.

### Contracts and street incidents

`quests.rs` owns ordered contract progress and compatible interpretation of older active contracts. `world_events.rs` owns each shard's street incidents: warnings, shared repairs, bounded enforcement waves, telegraphed hazards, hold meters, success/retry windows, and contributor credit. Incident actions validate the current cycle, time, living character, instance, sightline, and distance. The server advances only the current saved objective, and ordinary giver turn-in remains the only contract reward path. Incident machines do not respawn or grant kill rewards. World incidents and their snapshots exclude dungeon characters; queued characters in the expedition shard's city may participate in that shard's incidents.

Incident state is transient and fully represented in snapshots, so a dropped notification does not lose controls, hazards, deadlines, or status. Character `questStages` cursors are persisted and exported with the existing version-2 character. Stages default to absent on old saves; old active contracts retain their original single objective. Completed neighborhood story changes remain personal, while incident lights, work interruptions, recovery, and enforcement are shared within a shard. A restart resets live incidents without resetting saved quest steps.

### Expedition authority and queue

`dungeons.rs` owns an additional expedition shard using the existing simulation and persistence writer. On an eligible queue request, the home shard transfers the complete live `Player` through a bounded channel. The destination acknowledges ownership or returns the player if full. Cooldown deadlines and combat times shift to the destination simulation clock; movement recordings are discarded. The original home shard forwards subsequent socket actions, social transactions, signed-export requests, and disconnects, preserving the existing authenticated ID route. No intermediate save/rejoin or duplicate character lease is involved. Shutdown drains home shards before the expedition shard. Queueing does not modify persistent community parties.

One FIFO ticket per character selects one dungeon. Exact-size groups enter a 30-second ready check; acceptance is explicit, and only accepted, living runners retain their original priority after a decline or timeout. All participants must be alive before entry. Queue admission checks the dungeon level and out-of-combat state, with no lineage, faction, class, talent, or equipment restrictions. Queued runners may continue playing in the expedition shard's city. Once transferred, a character stays on that shard until disconnect, including after queue cancellation or a completed run. The 256-slot ceiling includes these city residents; a busy expedition shard can reject a transfer while ordinary home shards still have room.

Each private run has a server-issued ID and separate enemies, evidence, signatures, readiness sets, ballots, hazard timing, recovery cooldowns, and revive allowances. All arenas occupy the same reserved map square, isolated by an instance ID on players and enemies. Snapshots, enemy targeting, direct/area attacks, healing, shields, and Ghostline contact/damage/events enforce that ID. Movement stays inside the square. World quest/lift/shop actions are unavailable in an instance. The client submits intentions with run, chapter, and encounter-attempt tokens; it cannot submit evidence counts, enemy deaths, vote totals, XP, or gold. Lost presentation messages recover through subsequent snapshots.

Each chapter begins in a safe reading pause until every member is ready. Combat completion requires all encounter machines disabled, both evidence stations visited within 4 m, and every member signing at least one station. Three-second warnings and rectangle geometry match hazard damage. A marked station restores 45% maximum health on a personal 12-second cooldown; every member may revive allies twice per encounter within 4 m. A full wipe resets the current chapter after five seconds. Chapter completion restores the crew, clears echoes, and preserves earlier discoveries. There is no composition-dependent gate, simultaneous plate puzzle, or damage enrage.

The final ballot closes after every member votes or 90 seconds. Ballots can change until closure; missing ballots count as abstentions. A unique plurality wins; ties or an abstention plurality use the authored provisional ending. Individual ballots remain distinct from the group outcome. Completion is consumed before awarding each member the same base reward once; dungeon kills grant no ordinary XP, gold, or world-quest progress. Existing founder XP rules apply. The character's `dungeonHistory` stores a bounded per-dungeon clear count and last ending.

Queues/runs are transient. Leaving or disconnecting during an unfinished run ends it for everyone; complete runs let members leave independently. There is no reconnect reservation or mid-run backfill. A 90-minute lifetime bounds abandoned runs. A persisted `dungeonReturn` marker sends a character saved in an arena back to the Commons on the next connection, including after process failure. Completion rewards use ordinary character checkpoints and can be lost within that existing crash window; they are not durable economic transactions. The one-person dungeon runs on the same expedition shard; client prediction cannot advance it. Initial tuning, live cross-shard integration, and human group balance still need release validation.

## Plaintext storage

Runtime records live outside the public client directory:

```text
server/data/
  .instance.lock
  accounts/<normalized-username>.json
  characters/<random-character-id>.json
  social.json
  signing-key.json
```

Account JSON contains a schema version, username, Argon2id PHC password hash, and owned character IDs. Passwords are never written as plaintext. Character JSON contains the schema version, owner, character state, monotonically increasing character revision, and absolute cooldown deadlines. The deadlines preserve cooldowns across reconnects and process restarts. Unversioned account/character records are version 1, migrated in memory and written as version 2 at their next save. Unknown versions are rejected. A database file lock prevents two instances from writing the same directory.

A bounded queue hands snapshots to a dedicated disk thread. Checkpoints are scheduled every ten seconds, and disconnect/shutdown queues a final save. The writer serializes readable JSON, flushes the file, atomically renames it, and syncs the parent directory on Unix. It releases the character's active lease only after the final save succeeds. Disk errors retain the lease and retry the ordered write, preventing a stale disk save from being rejoined while a newer save is still pending.

Ordinary gameplay is checkpointed: a process or power failure can lose changes since the last durable checkpoint, plus queue delay. Social/economic mutations use the stronger transaction boundary below. Disk failure can delay all character writes and shutdown because this release uses one character writer. Account/character creation writes the character before publishing ownership; a crash between those writes can leave an unreferenced character file. Deletion removes community directory entries and invitations, then account ownership, then the character file; interrupted deletion can leave an unreferenced file but cannot transfer ownership. Historical contributions remain in the community archive. Runtime data should be backed up and monitored separately from source.

## Community and economic transactions

`GET /api/characters/{id}/social` reads a selected view (`summary`, `chat`, `dm`, `forum`, `auctions`, `deliveries`, `guilds`, or `people`). It authenticates account ownership. Chat and forum requests independently enforce the character's lineage and current group membership; DM queries select only conversations involving that character. Posts/threads use monotonically increasing IDs and exclusive `before` cursors, with 40 records per page. Directory search uses a paginated alphabetical-ID listing. Histories survive disconnects and server restart, and are never trimmed to a recent-message ring buffer. The client polls at five-second intervals, preserves composing forms, and pauses automatic history refresh while browsing older pages.

`POST /api/characters/{id}/social` accepts a version-2 action and unique `requestId`. It requires authentication, Origin/request marker checks, account-level rate limits, and an active owned character. The owning shard serializes it with gameplay. A blocking worker takes the shared community lock, stages a copy, validates permissions/resources, and atomically replaces `social.json`. Only a successful write publishes the staged state and updates the live character. The file contains the community records, auction escrow, pending deliveries, request receipts, and the initiating character's complete state at that transaction. Old queued character checkpoints cannot supersede that recovery record: reload chooses the highest character revision. Retried request IDs return their stored result; reuse with different content is rejected. Failure before publication leaves the old state intact. If rename succeeds but directory sync fails, the database refuses subsequent writes and exports until restart, avoiding another transaction against stale memory.

Listing removes the selected catalog item from the seller's pack; equipped items must be unequipped first. Bids debit gold into escrow; increasing one's own bid debits only the difference, and outbid players receive refund deliveries. Buyout or expiry settles once, sending the escrowed item stack to the buyer and proceeds minus a 5% fee (rounded up) to the seller. Cancelled or unbid expired listings return their items. Claims move gold/items into the claimant's character in the same transaction; a full item stack or medkit pack leaves unclaimed items in the delivery. Item searches, filters, and exact unit-price or metadata sorting run across the matching market before stable cursor pagination. Crafting, vendor sales, equipment swaps, and provision consumption use this same durable transaction path; ordinary loot and remaining buff time use gameplay checkpoints. Expiry uses absolute Unix seconds, runs on startup and every 30 seconds, and also runs before browsing or mutating community state. Gifts and daily supplies use the same delivery/claim mechanism.

Guilds have at most 100 members and parties at most eight. Leaders manage officer roles and transfer ownership; officers can invite, remove ordinary members, and edit guild tabards. Joining requires an invitation and an eligible lineage. A leader must transfer ownership before leaving other members behind. Persistent contacts require acceptance; blocks prevent DMs, gifts, and new invitations and hide the blocker's public chat/forum view. Completing a lineage quest unlocks 18 daily gold, or 36 while in a guild reserved for the character's lineage, with a once-per-UTC-day receipt.

Community state spans shards, but parties do not move members between physical world instances. A single in-memory JSON document with whole-file atomic replacement favors inspectable, reliable transactions over high write throughput. Histories and receipts grow with use, and writes clone/serialize the document. Measure community file size, lock time, latency, and memory before increasing population; this implementation is not a claim of large-MMO capacity. Split/archive storage would need to preserve transaction recovery and complete historical browsing.

## Moral decisions and personal consequences

`morality.json` supplies one decision definition per contract and expedition, shared consequence profiles, route commitments, relationship labels, and six bound equipment modifications. Both startup validators require complete coverage, valid references, distinct choice IDs, bounded effects and gear stats, and matching expedition ballot IDs. `morality.rs` owns mutation; the client module renders previews and consumes authoritative snapshots.

The additive, default-empty character `morality` object contains immutable choice records, bounded value/faction/neighborhood/contact scores, current route commitments, outstanding breach counts, modification imprints, and the fitted modification. These fields use ordinary version-2 snapshots, checkpoints, social transaction character copies, and signed exports. Missing old fields are neutral; earlier completions are never backfilled with guessed choices. Old active contracts retain their original objective interpretation.

A `quest` completion must include `choice`. After living-character, instance, giver proximity, visibility, objective readiness, and uncompleted-contract checks, the server validates the choice and any restitution eligibility before changing state. It applies consequences once, consumes the contract, grants its full XP and the selected percentage of base gold, and emits the selected outcome. A failed or duplicate action cannot spend a choice, gain an imprint, change standing, or receive another reward. Score changes clamp to ±100. A change of route commitment incurs an additional −3 local trust and −2 contact bond and adds one breach. Restitution on a subsequent contract of the same route pays zero gold, clears one breach, and leaves the current commitment and all prior records intact.

The first completed personal expedition ballot has a `dungeon:<id>` moral record. It is distinct from `dungeonHistory`'s latest crew ending. Missing ballots record neutral abstention. Later clears award their ordinary XP/gold but never repeat moral consequences. Shared votes and world incidents do not directly alter another character's moral state.

`moralGear` with a modification ID (or an empty ID to remove it) selects one earned modification while alive outside an expedition. One, five, and twelve earned imprints give three ranks; matching value requirements determine whether its stats are active. Client prediction and server `Stats` add those bonuses before existing caps and resurrection sickness. Changes clamp current health/energy to their maxima without healing. Bound modifications use their own saved slot, so a full pack cannot discard a quest consequence or allow it to be sold or auctioned.

Only Patch's existing medkit and coil-upgrade purchases use local trust pricing: market trust at +20/+8/−8/−20 gives 85/95/110/120% of base price (100% otherwise), rounded up by both implementations. Other economy prices are unchanged. The journal presents faction and contact relationships; NPC responses, civilian greeting/withholding behavior, selected neighborhood outcomes, narration, and final kitchen reception derive from that character's saved state. These are local presentation, not independent NPC inventories or a persistent shared population. A hostile relationship cannot block the campaign or essential services.

## Character portability

`GET /api/characters/{id}/export` obtains an owned character's current authoritative snapshot from its shard, or an offline snapshot under the admission lock, and signs it with Ed25519. The startup-generated private seed is persisted once in `signing-key.json`; corrupt/unsupported keys fail startup rather than being silently replaced. `GET /api/signing-key` publishes only the verification key. See [formats](FORMATS.md) for the exact signature envelope, ownership scope, and trust requirements. Export does not introduce an online import endpoint.

## Account protections

Authentication hashing runs in a bounded blocking pool with four concurrent slots. Registration uses independent 128-bit random salts; sessions use 256-bit OS randomness. Cookies are HttpOnly and SameSite=Strict, with Secure enabled for HTTPS deployments. Sessions expire after 24 hours and are invalidated on server restart. Per-IP account attempts are rate limited; the service does not trust forwarded client-IP headers automatically. A reverse proxy should apply its own per-client limits when many users share the proxy's upstream address.

Origins are an explicit allowlist. HTTP mutation requests require a custom marker as well as an allowed Origin; no permissive CORS handler is installed. WebSocket admission checks the Origin and account ownership, and a character can have one active lease. API bodies and socket frames are bounded. Public static serving is limited to client sources/assets and the license, with canonical path containment. The database and arbitrary repository files are not served.

The service and world simulation live in `main.rs`; `config.rs` handles listener/origin/thread configuration and `web.rs` serves public files; `social.rs` holds community storage, transactions, signing, and their tests. Seven direct dependencies provide HTTP/WebSockets, async scheduling, JSON, serialization, password hashing, OS randomness, and Ed25519. The browser predicts movement and presents server snapshots; Rust owns the full gameplay simulation. Shared JSON and deterministic map tests reduce movement drift but do not replace live integration testing.

## Long progression and modular equipment

`progression.rs` owns the 1,100× XP cost, quarter-level point budget, prerequisite and capstone checks, work orders, and one-time progression migration. The browser shares those formulas through `progression.js`. Existing levels and fractional XP survive the migration; previous flat talents are refunded. Currency fields serialize as `gold` and deserialize the old `credits` name, including delivery escrow. Restart server and clients together when upgrading.

The small component catalog in `economy.json` expands once into 24,000 stable item/recipe variants on both server and client. Rust indexes IDs, recipes, and tier/rarity loot pools; browser item lookups are indexed and catalog views paginate before rendering. Inventory is limited to 160 distinct stacks to bound save and snapshot growth. Overflow loot converts to gold; purchases and inventory actions reject insufficient capacity before spending. Auctions retain overflow in delivery escrow. Modular salvage and paid respecialization use the durable social transaction path. Work-order kills and payouts use the normal gameplay checkpoint guarantee.
